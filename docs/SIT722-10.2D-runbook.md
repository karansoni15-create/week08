# SIT722 10.2D runbook

This branch extends the Week 08 application. It does not contain Terraform
state, local variable values, Azure credentials, or evidence screenshots.

## Before running the pipeline

1. Confirm that the Week 08 Azure resource group, ACR, AKS cluster (three
   nodes), and storage account exist. The previous 8.1P report recorded their
   removal, so recreate them from your existing local Terraform state and
   `terraform.tfvars` if they are absent. Inspect `terraform plan` before
   applying. Do not run `terraform apply` against existing resources with an
   empty or unrelated state file.
2. Keep the existing GitHub `AZURE_CREDENTIALS` secret and repository variables
   `ACR_NAME`, `AKS_RESOURCE_GROUP`, and `AKS_CLUSTER_NAME` configured.
3. Add repository variable `DOCKERHUB_USERNAME` and repository secret
   `DOCKERHUB_TOKEN` (a Docker Hub personal access token). Docker Scout needs
   Docker Hub authentication even when it scans the locally built ACR-tagged
   image.
4. Keep `terraform.tfvars`, `terraform.tfstate`, `tfplan`, and `.terraform/`
   local. The `.gitignore` prevents accidental commits of these files.

## Pipeline order

1. `01 - CI`: backend tests and Terraform format, init, validate, Azure login
   check; then build each image, run Docker Scout CVE and recommendation
   reports, and push the same SHA-tagged image to ACR.
2. `02 - Deploy to Staging`: deploy that SHA to AKS staging; install the
   Prometheus/Grafana Helm chart, ServiceMonitor, and dashboard ConfigMap.
3. `03 - Test Staging`: check the frontend, the user service `/metrics`
   endpoint, and monitoring resources.
4. `04 - Deploy to Production`: manually enter the full 40-character commit
   SHA that passed CI and staging. Production uses those images without a
   rebuild.

Terraform validation runs without state on the GitHub runner. Infrastructure
creation remains a deliberate local `plan`/`apply` using the existing state;
automatic apply requires a shared remote state backend and a reviewed plan.

## Monitoring checks and screenshots

After staging succeeds, run these commands from PowerShell with AKS credentials:

```powershell
kubectl get nodes
kubectl get pods -n staging
kubectl get pods -n monitoring
kubectl get servicemonitor koalatech-user-service -n monitoring
kubectl port-forward -n monitoring svc/koalatech-monitoring-grafana 3000:80
```

Open `http://localhost:3000`. In another PowerShell window, retrieve the
Grafana password from the Kubernetes Secret:

```powershell
$encoded = kubectl get secret koalatech-monitoring-grafana -n monitoring -o jsonpath='{.data.admin-password}'
[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($encoded))
```

The username is `admin`. Open **KoalaTech Operations** and capture both the
replica and HTTP request panels. If the request panel is empty, call the user
service `/health` endpoint and wait at least one scrape interval. In Prometheus,
query `up{service="user-service"}` and
`koalatech_http_requests_total` to confirm collection.

For the brief report, capture:

- Updated workflow files and the `terraform-check` job logs.
- A Docker Scout CVE result and recommendation, followed by the changed base
  image or dependency and a second scan showing the effect. State the exact
  vulnerability and version rather than assuming that an update fixed it.
- Monitoring Pods and ServiceMonitor, Prometheus target/query results, and
  the Grafana dashboard with data.
- Green CI, staging deploy, staging test, and manually promoted production
  runs; ACR images and a working frontend.

The first scan determines which vulnerability is practical to remediate. Do
not claim remediation until the before/after reports demonstrate it.
